# dsh-time-machine Phase 2 (1.0 candidate) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add watcher-assisted scanning, rename detection, complete three-way conflict UI, and richer timeline filters to make dsh-time-machine a 1.0 candidate.

**Architecture:** Keep the existing core/host/client split. Core gains pure watcher debounce logic, rename matching in the diff layer, and restore preview content/force support. Host wires Node `fs.watch` recursive as a fast hint source while retaining scan as the source of truth. Client adds filters and per-conflict actions backed by new API routes.

**Tech Stack:** Node built-in `fs.watch`, TypeScript, React (client), Vitest + jsdom + node smoke/e2e.

## Key decisions

- Rename is stored as a single `FileChange` with `status: 'renamed'` and `oldPath`; restore planning expands it back to old+new paths.
- Watcher is only a hint. `recordAmbient` always follows with a full scan for final consistency.
- Force overwrite only overrides `conflict`; `dirty-before-session` and `agent-did-not-create` remain hard blocks.
- Three-way contents are returned from preview only when `includeContents: true` to keep default payloads small.
